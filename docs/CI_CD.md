# Руководство по CI/CD

В этом файле подробно описано, как работает автоматизация сборки, тестирования и деплоя (CI/CD) в нашем проекте. Мы используем **GitHub Actions** для автоматизации всех процессов.

---

## 🛠 Основные файлы настроек

### 1. `.github/workflows/ci-cd.yml`
Это "сердце" нашей автоматизации. Здесь описаны инструкции (jobs) для GitHub.

**Основные этапы (Jobs):**
*   **Lint & Static Analysis**: Проверяет стиль кода (`ECS`), ищет потенциальные ошибки (`PHPStan`), проверяет безопасность зависимостей (`composer audit`) и правильность конфигураций Symfony.
*   **Unit Tests**: Запускает быстрые тесты (TestSuite `unit`). Зависит от успешного прохождения `lint`.
*   **Integration Tests**: Запускает тесты, требующие БД (TestSuite `integration`). Включает ожидание MySQL (`mysqladmin ping`) и проверку миграций (вперед/назад). Зависит от `lint`.
*   **Build & Push Docker Image**: Сборка образа (`Dockerfile.prod`) и сканирование уязвимостей (`Trivy`). Зависит от прохождения всех тестов.
*   **Deploy (Staging/Production)**: Деплой с помощью Helm. Staging обновляется при пуше в `main`, Production — при создании тега `v*.*.*`.
*   **Smoke Tests**: Проверка эндпоинтов `/health/live` и `/health/ready` после деплоя для гарантии работоспособности.

---

### 2. `docker/php/Dockerfile.prod`
Инструкция по сборке "коробки" (контейнера) с нашим приложением для сервера.

*   **Двухэтапная сборка (Multi-stage build)**:
    1.  **Stage builder**: Устанавливаются все инструменты разработчика, компилируются зависимости, очищается кэш.
    2.  **Stage production**: Берется чистый и легкий образ PHP, куда копируется только готовый код и необходимые библиотеки. Это делает итоговый образ маленьким и безопасным.
*   **Безопасность**: Приложение запускается от пользователя `www-data`, а не от суперпользователя (root).

---

### 3. `helm/charts/jte-test/` (Папка с настройками Kubernetes)
Здесь лежат инструкции для облачной среды (Kubernetes), которые объясняют, как именно запускать контейнеры.

*   **`values.yaml`**: Основные настройки приложения (реплики, лимиты ресурсов, параметры HPA).
*   **`values-staging.yaml`**: Настройки для тестового окружения (Staging).
*   **`values-prod.yaml`**: Специфичные настройки для "боевого" сервера (Production), включая повышенные лимиты.
*   **`templates/deployment.yaml`**: Описывает поды приложения. Включает `initContainer` "wait-for-db" для ожидания готовности базы данных перед стартом. Настроены `livenessProbe` (`/health/live`) и `readinessProbe` (`/health/ready`).
*   **`templates/migrations-job.yaml`**: Helm Hook (`pre-install`, `pre-upgrade`), который запускает миграции базы данных перед обновлением приложения.
*   **`templates/hpa.yaml`**: Настройка Horizontal Pod Autoscaler для автоматического масштабирования количества подов на основе нагрузки на CPU.
*   **`templates/configmap.yaml`**: Конфигурация Nginx и других сервисов.
*   **`templates/ingress.yaml`**: Правила маршрутизации внешнего трафика.

---

### 4. Проверки здоровья (Health Checks)
Файл `src/Controller/Api/v1/HealthController.php` предоставляет важные эндпоинты для мониторинга:

*   **/api/v1/health/live**: Liveness-проба. Подтверждает, что PHP-процесс жив.
*   **/api/v1/health/ready**: Readiness-проба. Проверяет доступность всех зависимостей (MySQL, Redis, Manticore) и актуальность миграций. Используется Kubernetes для направления трафика и в CI для Smoke-тестов.

---

### 5. `phpunit.dist.xml`
Настройки для тестов. Указывает, где лежат тесты и как подключаться к тестовой базе данных. В CI/CD используется переменная окружения `DATABASE_URL`, которая переопределяет локальные настройки.

---

## 🔄 Как происходит процесс разработки

1.  **Pull Request**: Когда вы создаете PR в ветку `main`, запускаются проверки (Lint и Tests). Деплой на этом этапе не происходит.
2.  **Push в `main`**: После слияния кода в `main`, запускаются тесты. Если всё ОK — приложение автоматически обновляется на **Staging** сервере.
3.  **Создание Tag (Версии)**: Когда вы создаете тег (например, `v1.0.0`), запускается процесс деплоя на **Production** (боевой сервер).

## 🛡 Безопасность и секреты

Все важные данные хранятся в **GitHub Secrets** (`Settings -> Secrets and variables -> Actions`).

**Ключевые секреты:**
*   `GITHUB_TOKEN`: Для публикации Docker-образов в GHCR.
*   `KUBECONFIG_STAGING` / `KUBECONFIG`: Ключи доступа к Kubernetes.
*   `DATABASE_URL`: (в CI) URL для подключения к временной MySQL.

## 🗄 Миграции и база данных

1.  **В CI**: Миграции проверяются в `Integration Tests` (прогон вперед и откат).
2.  **При деплое**: Используется Helm Job (`migrations-job.yaml`), который запускается ПЕРЕД обновлением кода приложения. Если миграции упадут, деплой прервется, и старая версия кода продолжит работать.
3.  **Ожидание**: Все компоненты (тесты, Job, само приложение) используют скрипт ожидания доступности порта БД для предотвращения ошибок при холодном старте контейнера MySQL.
