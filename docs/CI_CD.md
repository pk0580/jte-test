# Руководство по CI/CD

В этом файле подробно описано, как работает автоматизация сборки, тестирования и деплоя (CI/CD) в нашем проекте. Мы используем **GitHub Actions** для автоматизации всех процессов.

---

## 🛠 Основные файлы настроек

### 1. `.github/workflows/ci-cd.yml`
Это "сердце" нашей автоматизации. Здесь описаны инструкции (jobs) для GitHub.

**Триггеры (When it runs):**
*   **Pull Request в `master`**: Запускает проверки кода и тесты.
*   **Push в `master`**: Запускает тесты, сборку образа и деплой на **Staging**.
*   **Создание тега `v*.*.*`**: Запускает сборку образа и деплой на **Production**.

**Основные этапы (Jobs):**
*   **`lint` (Lint & Static Analysis)**:
    *   Проверяет стиль кода (`ECS`).
    *   Статический анализ (`PHPStan` уровень 5).
    *   Аудит безопасности зависимостей (`composer audit`).
    *   Валидация конфигураций Symfony (container, yaml, twig).
    *   Проверка схемы базы данных Doctrine.
*   **`unit-tests` (Unit Tests)**:
    *   Запускает быстрые изолированные тесты.
    *   Зависит от успешного прохождения `lint`.
*   **`integration-tests` (Integration Tests)**:
    *   Запускает тесты, требующие реальную БД (MySQL 8.0 в контейнере).
    *   Проверяет миграции (накатывание, откат и повторное накатывание).
    *   Генерирует отчет о покрытии кода тестами.
    *   Зависит от `lint`.
*   **`package` (Build & Push Docker Image)**:
    *   Собирает Docker-образ с помощью `Dockerfile.prod`.
    *   Присваивает теги: SHA коммита, имя ветки, версия (из Git Tag) и `latest`.
    *   Сканирует итоговый образ на уязвимости с помощью **Trivy**.
    *   Зависит от прохождения всех тестов.
*   **`deploy-staging` (Deploy to Staging)**:
    *   Деплоит приложение в пространство имен `staging` с использованием Helm.
    *   Использует файл `values-staging.yaml`.
    *   Зависит от успешной сборки образа.
*   **`smoke-tests` (Smoke Tests)**:
    *   После деплоя на Staging проверяет доступность эндпоинтов `/health/live` и `/health/ready`.
    *   Использует механизм ретраев (5 попыток) для ожидания старта приложения.
*   **`deploy-production` (Deploy to Production)**:
    *   Деплоит приложение в пространство имен `production`.
    *   Использует файл `values-prod.yaml`.
    *   Настроена стратегия `atomic` (автоматический откат при неудаче).
    *   Зависит от успешного прохождения Smoke тестов на Staging.

### 2. `.github/actions/php-setup/action.yml`
Это переиспользуемый композитный экшен (Composite Action), который унифицирует настройку окружения PHP во всех джобах CI/CD.

**Что он делает:**
1.  **Устанавливает PHP 8.4** с необходимыми расширениями (`pdo_mysql`, `redis`, `soap`, `intl`, `bcmath` и др.).
2.  **Настраивает кэширование Composer**: Сохраняет директорию `vendor` и кэш загрузок между запусками пайплайна, что ускоряет установку зависимостей в 2-3 раза.
3.  **Устанавливает зависимости**: Запускает `composer install` с оптимизацией автозагрузчика. Использует механизм ретраев (3 попытки) для стабильности при сетевых сбоях.

---

### 3. `docker/php/Dockerfile.prod`
Инструкция по сборке "коробки" (контейнера) с нашим приложением для сервера.

*   **Двухэтапная сборка (Multi-stage build)**:
    1.  **Stage builder**: Устанавливаются все инструменты разработчика, компилируются зависимости, очищается кэш.
    2.  **Stage production**: Берется чистый и легкий образ PHP, куда копируется только готовый код и необходимые библиотеки. Это делает итоговый образ маленьким и безопасным.
*   **Безопасность**: Приложение запускается от пользователя `www-data`, а не от суперпользователя (root).

### 4. `helm/charts/jte-test/` (Папка с настройками Kubernetes)
Здесь лежат инструкции для облачной среды (Kubernetes), которые объясняют, как именно запускать контейнеры. Helm позволяет управлять сложными конфигурациями через шаблоны (templates) и параметры (values).

**Основные файлы конфигурации:**
*   **`Chart.yaml`**: Метаданные чарта (имя приложения, версия API, версия чарта).
*   **`values.yaml`**: Глобальные настройки приложения по умолчанию (реплики, лимиты ресурсов, параметры HPA, порты).
*   **`values-staging.yaml`**: Специфичные настройки для тестового окружения (например, меньшее количество реплик, другие хосты Ingress).
*   **`values-prod.yaml`**: Настройки для "боевого" сервера (Production), включая повышенные лимиты ресурсов и специфичные параметры окружения.

**Шаблоны (`templates/`):**
*   **`deployment.yaml`**: Описывает основные поды (pods) приложения. Включает:
    *   `initContainer` "wait-for-db": Ожидает готовности порта базы данных перед стартом основного приложения.
    *   `livenessProbe`: Периодическая проверка `/api/v1/health/live`. Если упадет — Kubernetes перезапустит контейнер.
    *   `readinessProbe`: Проверка `/api/v1/health/ready`. Пока она не пройдёт, трафик на под не направляется.
*   **`worker-deployment.yaml`**: Отдельный деплоймент для фоновых воркеров (Symfony Messenger). Запускает команду `messenger:consume` для обработки очередей.
*   **`migrations-job.yaml`**: Helm Hook (`pre-install`, `pre-upgrade`). Запускает `doctrine:migrations:migrate` ПЕРЕД обновлением кода приложения. Гарантирует актуальность схемы БД.
*   **`cronjobs.yaml`**: Описание запланированных задач (Kubernetes CronJobs), например, очистка логов или генерация отчетов по расписанию.
*   **`service.yaml`**: Внутренний балансировщик, который предоставляет стабильный IP/DNS для доступа к подам внутри кластера.
*   **`ingress.yaml`**: Настройка внешнего доступа (Nginx Ingress Controller). Определяет доменные имена и правила маршрутизации HTTPS трафика.
*   **`hpa.yaml`**: Horizontal Pod Autoscaler. Автоматически увеличивает количество подов при росте нагрузки на CPU или память.
*   **`configmap.yaml`**: Хранилище текстовых конфигураций (например, настройки Nginx или PHP-FPM).
*   **`_helpers.tpl`**: Вспомогательные функции и переменные, используемые в других шаблонах чарта.

### 5. Проверки здоровья (Health Checks)
Файл `src/Controller/Api/v1/HealthController.php` предоставляет важные эндпоинты для мониторинга:

*   **/api/v1/health/live**: Liveness-проба. Подтверждает, что PHP-процесс жив.
*   **/api/v1/health/ready**: Readiness-проба. Проверяет доступность всех зависимостей (MySQL, Redis, Manticore) и актуальность миграций. Используется Kubernetes для направления трафика и в CI для Smoke-тестов.

---

### 5. `phpunit.dist.xml`
Настройки для тестов. Указывает, где лежат тесты и как подключаться к тестовой базе данных. В CI/CD используется переменная окружения `DATABASE_URL`, которая переопределяет локальные настройки.

## 🔄 Как происходит процесс разработки

1.  **Pull Request**: Когда вы создаете PR в ветку `master`, запускаются проверки (Lint и Tests). Деплой на этом этапе не происходит.
2.  **Push в `master`**: После слияния кода в `master`, запускаются тесты. Если всё ОK — приложение автоматически обновляется на **Staging** сервере.
3.  **Создание Tag (Версии)**: Когда вы создаете тег (например, `v1.0.0`), запускается процесс деплоя на **Production** (боевой сервер).

## 🛡 Безопасность и секреты

Все важные данные хранятся в **GitHub Secrets** (`Settings -> Secrets and variables -> Actions`).

**Ключевые секреты:**
*   `GITHUB_TOKEN`: Для публикации Docker-образов в GHCR.
*   `KUBECONFIG_STAGING` / `KUBECONFIG`: Ключи доступа к Kubernetes.
*   `DATABASE_URL`: (в CI) URL для подключения к временной MySQL.

## 🗄 Миграции и база данных

1.  **В CI**: Миграции проверяются в `Integration Tests` (прогон вперед и откат).
2.  **При деплое**: Используется Helm Job (`migrations-job.yaml`), который запускается ПЕРЕД обновлением кода приложения. Если миграции упадут, деплой прервется, и старая версия кода продолжит работать.
3.  **Ожидание**: Все компоненты (тесты, Job, само приложение) используют механизмы ожидания доступности порта БД для предотвращения ошибок при "холодном старте" MySQL.
    *   В **CI/CD** (Integration Tests): используется `mysqladmin ping` прямо в описании джобы.
    *   В **Kubernetes** (Staging/Production): скрипт проверки порта на PHP реализован внутри `initContainer` "wait-for-db" в файле `helm/charts/jte-test/templates/deployment.yaml`. Он делает до 30 попыток подключения с интервалом в 2 секунды перед запуском основного контейнера.
